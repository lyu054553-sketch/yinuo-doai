### 一、正负极性（否定要求不再当成正向需求）

- 新增 `_is_negated()`：在**同一小句**（到逗号/分号/句号为止）内、词前出现
  “不要/别/无/没有/不含/未见/无需”等否定词，就判为否定要求，否定作用不会跨逗号。
- 颜色、纹样分组后逐条核对：
  - 否定要求（“不要红色/不要梅花”）**缺席不报**；方案里反而出现才判 `有冲突`；
  - 方案写法里的否定（“不含红色”“未见可辨认的梅花”）用 `_value_contains()` 判为“方案里没有”，
    所以客户要这个颜色/纹样、方案写的是否定描述时，仍判被改写/未落实；
- 定性完全基于通用词与标点，未引用任何评测特殊词表。

### 二、允许替代与明确组合、多组约束

- 一句话里的颜色/纹样要求按连接词分组：`或/还是/也可以/都行/二选一` → **满足其一即可**；
  `和/与/以及/＋/拼色/拼接` → **必须同时满足**（部分满足判 `被改写`，全缺判 `未落实/被改写`）；
  无连接词则各自独立成组，**不再只取第一组**。
- 同义词仍按组核对：`暗纹`与`暗花`互为实现，客户说“暗纹”、方案写“植物暗花”不误报。
- `ensure_mappings` 只为**正向**纹样要求补中性映射，“不要梅花”不再被补成正向要求。

### 三、材质出处（只说“资源库暂无对应参考”，不断言现实不存在）

- 新增 `_check_fabric_provenance()`：**仅当**方案 `面料` 栏 `origin=已有方案`、
  取出的片段是**具体材料名**（含棉麻丝毛绒呢绸缎纱锦革皮纶纤等材质字），
  且该片段在**可推荐**面料资源的名称/别名里找不到对应时，把相关
  `已落实/间接体现` 的面料映射升级为 `需设计师判断`，理由写“资源库暂无对应参考，请核实来源”。
- 纯属性描述（哑光、有肌理、挺括、垂感、光泽等）在剥离属性词后没有具体料名，**不报**；
  已知名称/别名（如 提花宋锦、宋锦、醋酸、香云纱、缎面）能对应到资源，不报；
- 参考范围只用 `knowledge.resources_for_field("面料")`（已排除只有留出来源的条目），
  不把留出条目当白名单；未按任何具体样布名写规则。

### 一、按资源名/别名做正负向匹配（修“面料想用醋酸却选了宋锦”）

- `pipeline/match.py` 新增 `_aliases()`：把资源名称（含名称第一段）和
  `knowledge_attrs.json` 里已有的 `match_keywords` 合起来，作为“客户可能点名的资源词”。
  **没有按任何具体案例硬编码**。
- `_mentions()` + `_negated()` 判断资源词在原话里是正向还是被否定（“不要醋酸”“不要交领”）；
- `_score()` 现在会把正向点到的资源词加分（命中名称 +3、命中别名 +2，硬约束再 +2），
  所以“面料想用醋酸”这类**软偏好**也会真正选中 F1 醋酸面料，而不是回落到宋锦；
- `_wanted_filter()`：被否定的资源直接排除、绝不反向加分；客户**硬点名**了可满足的资源时
  （“面料一定要醋酸”），只保留能满足的资源，避免被换成别的材料；
- 纹样、颜色的取词也改用“正向出现”判断，“不要梅花”里的“梅花”不会再被当成要求。

### 二、里料不能当外套主面料

`_fabric_allow()`：属性 `用途=里料` 的资源（F4 真丝里布）只有原话明确提到“里料/里布/内衬/
衬里/里子”时才进候选，默认取最常见面料时也会排除。不编库存、不把里布拼成主面料。

### 三、修 SH3 肩型被反向排除的 bug

原 `_shoulder_allow` 写成 `attr 压肩 is not False`，要求“不压肩”时反而**排除**了
`压肩=False` 的 SH3。现改为只保留 `压肩 is False` 的肩型（SH3），并要求出现
“不压肩/不能压肩/不要压肩/别压肩”任一说法都生效。

### 四、八栏顺序固定

`build_initial_spec()` 末尾按 `FIELD_ORDER` 重新组装返回字典，修正了此前“装饰纹样”
排在“色彩”前面、与约定第 4/5 节顺序不一致的问题。

### 五、多件套按单品分别匹配（不丢单品、不伪造拼合）

- `Want` 带上 `mapping.garment`；新增 `_garment_scopes()`：两件式套装按“外套、连衣裙”
  分别匹配，客户没指定单品的共享要求对两个单品都生效；
- 版型（廓形+肩型）、领型、面料、长度、松弛余量都按单品分别选资源，
  字段值写成 `外套：……；连衣裙：……`（约定第 5 节的多件套写法），资源 id 合并去重、
  每一项都来自它自己的单品；
- 某个单品匹配不到（例如“腰部要宽松”的连衣裙在资源库里没有不收腰的裙廓形）：

（`已与客户确认` 是系统追加状态，仍不出现在提示词里）。M3 有用例锁死这个顺序。

### 五、未处理异常统一为中文 JSON 500

`main.py` 增加 `Exception` 兜底处理：任何没预料到的异常都返回
`500 {"error": "服务器内部出现异常，本次操作没有完成，请稍后重试；……"}`，
**不返回堆栈、不返回异常原文**（异常原文里可能带接口密钥、路径），细节只写服务端日志。
原有 4xx 的 `{"error": ...}` 口径不变。

### 六、并发稳健性

- `store.py` 新增 `session_lock(session_id)`：按会话 id 的可重入锁上下文（`RLock`），
  不同会话各自一把锁、互不阻塞；使用计数归零后回收锁对象。
  **这是核心内部协作 helper，不改任何冻结的 HTTP 接口和 schema 字段**；
  出图与视觉若要复用，直接 `from app.store import session_lock` 即可（本代理不改媒体文件）。
- `save_session` 仍是“临时文件 + `os.replace`”原子写，临时文件名加随机后缀，并发写不会互相覆盖。
- `routers/sessions.py`：`/answers` 与 `/spec` 的“读—改—写”全程加 `session_lock`，
  同一问题并发重复提交只升一个版本、只记一条台账；两个不同修改并发也不会互相覆盖。
