## 2025-11 里程碑 D0：评测脚手架（已完成，待总控运行）

### 做了什么

- 新增 `eval/run_eval.py`（单文件、只用 Python 标准库，不依赖第三方包，不导入后端代码）。
- 评测对象通过 HTTP 调用：
  - `GET /api/health`：记录 `mock_mode`、`llm_model`、`image_provider`
  - `GET /api/samples`：只按白名单取开发集样例（API 展示 6 个案例，脚本只使用 c1、c2、c3、c4、c6）
  - `POST /api/sessions`：每次重复创建一个“审计已有方案”会话
- 标准答案只从 `data/cases.json` 读取开发集（c1、c2、c3、c4、c6）。**c5 在参数校验阶段就被硬性拒绝**，任何参数都无法为它创建会话；脚本也不会用 c5 的标准答案参与任何计算。
- 指标实现（按任务 D 的定义）：
  1. **拆句**：预测原话与标准原话用字符重叠配对（最长公共子串 / 较长者长度 ≥ 0.5，一对一贪心），报告召回率与精确率。
  2. **字段对应**：只看配上的原话，比较字段集合，报告召回率与精确率（微平均）。
  3. **问题检出**：标准状态属于 {有冲突, 被改写, 未落实, 需设计师判断} 的句子为“问题句”；逐句列出是否检出；统计误报（标准为非问题句、预测报成问题状态）。
  4. **状态一致率**：六种状态逐句完全一致率；另单独报告“间接体现/已落实合并”的宽松一致率，不与问题检出混算。
  5. **不编造**：逐条检查原话是否为原文子串、`start/end` 是否与原文一致、方案字段与追问选项引用的资源 id 是否存在于 `data/resources.json`；并统计每份方案 `origin=无出处` 的栏数。
  6. **稳定性**：每个案例默认重复 3 次，比较各次问题检出结果（每条问题句是否检出 + 误报 id）是否一致。
  7. **耗时**：记录每次 `POST /api/sessions` 的毫秒数，报告均值与逐次值。
- 记录每次会话的 `source`、`created_at`、`mode`、`sample_id`、方案版本，以及后端 `health` 中的模型名与 mock 状态。
- 原始输出全部落盘到 `eval/runs/<运行编号>/`：`cX_rN.session.json`、`cX_rN.metrics.json`、`calls.jsonl`、`summary.json`、`samples_dev_only.json`。
- 报告输出到 `eval/reports/<tag>_评测脚手架报告.md`，每次运行覆盖同名报告，同时保留 `runs/` 下的原始数据。

### 怎么运行

```bash
# 后端已在 8100 端口以 MOCK_MODE=1 启动后：
python eval/run_eval.py
python eval/run_eval.py --base-url http://127.0.0.1:8100 --repeats 3
python eval/run_eval.py --cases c1,c2      # 调试用
```

| 参数 | 默认 | 说明 |
|---|---|---|
| `--base-url` | `http://127.0.0.1:8100` | 后端地址 |
| `--repeats` | `3` | 每个案例重复次数 |
| `--cases` | `c1,c2,c3,c4,c6` | 只允许开发集；含 `c5` 直接拒绝运行 |
| `--data-dir` | 脚本上级目录的 `data/` | 标准答案与资源库位置 |
| `--timeout` | `120` 秒 | 单次 HTTP 超时 |
| `--allow-nonmock` | 关闭 | D0 中若后端非 MOCK 模式则拒绝运行；D2 需要时显式加上 |
| `--tag` | `d0` | 报告文件名前缀 |

退出码：`0` 完成且（MOCK 下）自检满分；`1` 运行出错；`2` 参数被拒绝（含请求 c5）或 MOCK 自检不满分。
